# FlowMesh 技术面试问答

> 由 `docs/technical-interview-qa.md` 整理而来；每个文档最多包含 200 组问答。

Q: 请介绍一下 FlowMesh 项目
A: FlowMesh 是一个面向 B2B SaaS 场景的多租户供应商准入与采购审批平台。当前版本由 Gateway、IAM、Supplier、Workflow、Risk 和 Notification-Audit 组成，支持用户登录、供应商申请、材料提交、异步风控、采购初审、法务/财务会签、启用、通知和审计。

项目重点解决四类问题：使用 JWT、RBAC 和 PostgreSQL RLS 实现多租户安全隔离；使用 `Idempotency-Key` 防止重复创建；使用 MyBatis 条件更新实现乐观锁，避免并发审批覆盖；使用 RocketMQ Transactional Outbox 保证跨服务事件最终一致性。

Q: 你本人具体负责了哪些模块？如何证明不是只会搭框架？
A: 回答应落到可验证的代码和决策上，例如：负责 Gateway 与多个领域服务的边界设计、数据库迁移、认证链路、申请幂等、Outbox 发布器、RLS、文件安全检查和 Testcontainers 集成测试。面试时应能打开代码说明一次请求如何经过 Gateway、Controller、Application Service、Repository、事务和事件发布，而不是只罗列技术名词。

Q: 为什么简历中不能把 Camunda、Redis 缓存和真实外部风控写成已落地能力？
A: 因为当前仓库使用内部状态机推进审批，Redis 已用于 Gateway 分布式入口限流和 IAM 登录限流，但没有作为业务缓存或幂等事实源；risk-service 使用可复现的模拟规则而非真实征信机构。MinIO 材料存储和独立 risk-service 已接入运行链路，但不能把尚未接入的 Camunda、Redis 缓存或外部风控供应商写成已落地能力。

Q: 申请提交后为什么不是直接进入采购审批？
A: Workflow 先创建 `RISK_CHECKING` 投影并通过 Outbox 发布 `RiskCheckRequested`。risk-service 消费后在本地事务中保存风控结果和 `RiskCheckCompleted`，Workflow 以事件 Inbox 做幂等；PASS 才进入采购初审，REJECT 进入终止状态。这样把外部风控延迟和失败重试从审批接口中隔离出来。

Q: risk-service 为什么也需要 Outbox？
A: 风控结果写入数据库和发布 RocketMQ 事件必须保持最终一致。如果结果已经落库但进程在发送前宕机，直接发送会丢事件；Outbox 让发布器按租约认领、收到 Broker ACK 后确认，失败按指数退避，达到上限后进入死信，Workflow 的事件 Inbox 再吸收重复投递。

Q: 为什么拆分成多个服务？
A:
- Gateway 负责统一 API 入口和下游路由，不拥有业务数据。
- IAM 负责租户、用户、角色、JWT 和 Refresh Token。
- Supplier 负责供应商申请及申请状态，是申请数据的唯一拥有者。
- Workflow 负责审批流程实例、当前任务和审批推进，是流程数据的唯一拥有者。
- Risk 负责异步风控结果和可重试的风险事件，不把外部风控延迟塞进申请接口。
- Notification-Audit 负责供应商启用后的站内通知和不可变审计投影，不直接承担外部邮件或短信发送。

这样拆分是按照业务能力和数据归属划分边界。服务之间不直接查询对方数据库，而是通过 REST 或 RocketMQ 事件交互，避免跨服务共享表和隐式耦合。

Q: 服务之间为什么不能直接共享数据库表？
A: 共享表会让服务之间形成隐式耦合，任何一个服务修改字段都可能影响其他服务，也会破坏数据归属和独立发布能力。Supplier 只拥有申请数据，Workflow 只拥有流程数据；跨边界需要通过 API 或事件传递明确的业务契约。

Q: Workflow 服务暂时不可用时，Supplier 创建申请会失败吗？
A: 不应该失败。Supplier 只需要在本地事务中提交申请和 Outbox 事件，Workflow 恢复后由发布器和消费者继续处理。用户可以看到申请已创建但审批流程处于“处理中”或“待同步”状态，这正是最终一致性系统需要明确呈现的业务状态。

Q: 一次供应商申请的完整链路是什么？
A: 用户先通过 IAM 登录获取 JWT。Supplier 校验 JWT 后，在一个本地事务中创建供应商申请和 `ApplicationSubmitted` Outbox 事件。Outbox 发布器将事件发送到 RocketMQ，Workflow 消费后创建对应的流程实例和当前任务。

采购、法务、财务和运营角色依次完成审批。Workflow 在任务完成后写入 `WorkflowTaskCompleted` Outbox 事件，Supplier 消费该事件并更新申请状态。整个链路不依赖跨服务分布式事务，而是通过本地事务、可靠消息和幂等消费实现最终一致性。

Q: 创建申请时，哪些操作必须在同一个事务中？
A: 供应商申请、Outbox 事件和首次幂等响应快照必须在同一个 Supplier 数据库事务中提交。RocketMQ 网络发送不能放在这个事务里，否则会长时间占用数据库连接，也无法把外部 Broker 真正纳入本地事务。

Q: 最终一致性会不会让用户看到错误状态？
A: 会存在短暂的中间状态，所以 API 和前端不能假设申请创建后流程实例立即可见。应该返回申请已提交，并通过查询、状态字段或异步刷新展示流程同步状态。对用户可见的状态必须与实际状态机定义一致，不能用“请求成功”掩盖后续处理失败。

Q: 当前项目哪些内容已经实现，哪些内容还没有实现？
A: 已经实现：统一 Gateway、IAM、Supplier、Workflow、Risk 和 Notification-Audit 六个服务，JWT 登录刷新登出、RBAC、多租户 RLS、供应商申请、材料上传与安全校验、持久化接口幂等、异步风控、通知审计、RocketMQ Outbox、重试/死信/受控重放、跨服务对账、Docker Compose、Helm 和 CI 校验。

尚未作为当前运行链路实现：Camunda 流程引擎、Redis 缓存、外部邮件/短信通道和生产级托管 Prometheus/Alertmanager/Grafana/OpenTelemetry 平台。Gateway Redis 分布式限流、Redis 登录限流、MinIO 材料存储、本地 Prometheus/Alertmanager/Grafana 基线、真实 RocketMQ Broker E2E、DLQ 查询/受控重放/审计、跨服务对账和基础业务消息指标已经实现；生产级外部依赖 HA 仍需在目标集群演练。

Q: 如果面试官质疑项目规模不够，你如何回答？
A: 应准确表述为“生产化基线”而不是完整的企业级托管平台。项目已经把服务边界、租户隔离、幂等、乐观锁、可靠消息、材料安全、风控、通知审计、基础观测和部署校验做成可运行闭环；但外部基础设施 HA、托管观测后端、真实通知通道和 Camunda 仍是明确的后续边界。

Q: 为什么选择 RocketMQ，而不是 RabbitMQ？
A: 本项目选择 RocketMQ，是因为项目需要面向领域事件的异步解耦、消费重试、延迟重试和后续死信处理能力。RocketMQ 的 Topic、Tag、消费重试和消息存储模型比较适合这种事件驱动链路。

RabbitMQ 也可以实现该方案，尤其适合复杂路由、低延迟任务和成熟 AMQP 生态。两者都不能单独解决业务数据与消息发送之间的一致性，所以最终关键不在于“选哪个 MQ”，而在于 Outbox、幂等、重试和故障恢复设计是否完整。

Q: 如果业务更看重复杂路由，你会改选 RabbitMQ 吗？
A: 有可能。RocketMQ 更贴近当前项目的 Topic/Tag、重试和延迟消息需求；RabbitMQ 的 Exchange、Binding 和 Routing Key 在复杂路由场景更自然。应基于吞吐、延迟、消息顺序、重试模型、运维能力和团队经验评估，而不是把某个 MQ 说成绝对更好。

Q: Transactional Outbox 解决了什么问题？
A: 它解决的是“业务数据已经提交，但消息没有成功发送”的问题。以创建申请为例，申请记录和 Outbox 事件在同一个 PostgreSQL 本地事务中提交：事务成功意味着待发送事件一定持久化，发布器之后可以继续发送。

如果直接先写数据库再发送消息，服务在两步之间宕机会丢消息；如果先发送消息再写数据库，则可能出现消费者先收到一个不存在对应业务数据的事件。Outbox 将两步拆开，并通过数据库记录保证事件不会因为进程短暂故障而丢失。

Q: Outbox 的本地事务提交顺序是什么？
A: 先在同一个数据库事务中写入业务记录和 Outbox 记录，数据库事务提交成功后才允许发布器读取该事件。发布器读取并认领事件，事务提交认领结果后再发送 RocketMQ；收到发送成功响应后，使用条件更新标记发布成功。

Q: 为什么不在业务事务中直接调用 RocketMQ？
A: 远程调用耗时和失败不可控，放在业务事务中会长时间持有数据库连接、扩大锁范围，并且数据库事务仍不能回滚已经发送到 Broker 的消息。Outbox 把本地持久化和远程发送解耦，故障窗口交给幂等和重试处理。

Q: Outbox 是否保证消息恰好发送一次？
A: 不保证。发布器发送成功后、更新 `published_at` 之前如果宕机，恢复后可能再次发送同一个事件。因此系统按至少一次投递设计，不能把 RocketMQ 或 Outbox 描述成恰好一次。

本项目通过事件 ID、消费者 Inbox 或业务唯一约束实现幂等消费；重复消息只会被识别并忽略，不会重复创建流程或重复推进申请状态。

Q: 为什么不能通过“发送后立刻标记成功”实现恰好一次？
A: 因为“发送成功”和“本地标记成功”之间仍然存在进程宕机窗口。只要这两个外部动作不在同一个可回滚的全局事务中，就可能出现消息已发送但数据库仍显示未发送。正确做法是接受至少一次投递，并保证消费者幂等。

Q: 多实例 Outbox 发布器如何避免重复抢同一批事件？
A: 发布器先在短数据库事务内使用 `FOR UPDATE SKIP LOCKED` 查询未发布且可重试的事件，并写入认领 token 和认领过期时间。不同实例会跳过已经被其他实例锁定或认领的记录。

认领事务提交后才进行 RocketMQ 网络发送，避免在数据库事务中长时间占用连接。发送成功后使用认领 token 做条件更新，只有当前认领者可以将事件标记为已发布。

Q: `FOR UPDATE SKIP LOCKED` 在这里具体解决什么问题？
A: 多个发布器并发扫描未发布事件时，行锁让一个实例锁定待处理记录，其他实例遇到已锁定行会跳过并继续获取其他记录，避免所有实例读取同一批数据后重复发送。它只解决数据库侧的并发认领，不能消除发送成功后的重复窗口。

Q: 实例在认领事件后宕机，事件会不会永久丢失？
A: 不会。认领记录带有过期时间，其他实例只会跳过仍在租约内的记录；租约过期后可以重新认领。认领和发布成功更新都使用条件判断，避免旧实例恢复后覆盖新实例的结果。

Q: 消息发送失败如何处理？
A: 发送失败会记录失败原因和尝试次数，并根据指数退避计算下一次尝试时间。超过最大尝试次数后，事件进入失败终态，记录 `dead_lettered_at`，避免无限快速重试造成数据库、线程池和 Broker 压力。

当前系统会记录失败状态和重试数据；进入死信后，只有 `OPERATIONS` 角色可以按租户、事件类型或聚合 ID 查询，并且必须填写原因才能生成新 `eventId` 重放。原事件、重放事件、操作者、租户、原因、状态和时间会写入审计表。

Q: 为什么要指数退避，而不是每秒重试？
A: 持续每秒重试会在 Broker、网络或下游长期故障时制造更多压力和日志噪声。指数退避让短暂故障可以较快恢复，持续故障逐步降低重试频率；最大尝试次数则保证错误最终进入可观测的失败终态。

Q: 如果 RocketMQ 已经 ACK，但服务在标记 Outbox 成功前宕机，会发生什么？
A: 同一事件可能再次发送，消费者会收到重复投递。消费者必须以事件 ID 或业务唯一键进行幂等判断：如果已经处理过，则直接确认消息，不再次执行副作用。

这是可靠消息系统中常见的“发送成功与本地状态确认之间的窗口”，不能靠单个数据库事务消除，只能通过幂等消费吸收。

Q: 消费者如何判断重复消息？只比较消息内容可以吗？
A: 不能只比较内容，因为相同内容可能代表不同事件。应使用稳定的 `eventId`，并结合消费者类型或业务唯一键建立持久化去重约束。重复消息到达时直接确认，不再次执行创建、状态变更或通知等副作用。

Q: 事件信封包含哪些字段？为什么要统一校验？
A: 事件信封包含 `eventId`、`eventType`、`schemaVersion`、`aggregateId`、`tenantId`、`occurredAt`、`traceId` 和 `payload`。公共模块对事件类型、版本号、UUID、租户长度、时间戳、追踪 ID 和载荷进行校验。

统一校验可以让消费者在边界处快速拒绝非法或不兼容消息，避免每个服务重复实现解析规则，也能降低事件结构变更导致的隐性兼容问题。

Q: 事件版本升级时，消费者应该怎么做？
A: 消费者先校验 `schemaVersion`。对兼容性的新增字段可以保持旧消费者可读；字段语义、类型或必填约束发生破坏性变化时应提升版本，并通过兼容窗口、双读或独立消费者逐步迁移，不能直接复用旧版本号。

Q: `Idempotency-Key` 的实现逻辑是什么？
A: 系统以 `tenantId + userId + idempotencyKey` 作为幂等作用域，并在数据库建立唯一约束。首次请求在事务中创建供应商申请、Outbox 事件和幂等记录，同时保存请求指纹、HTTP 状态码和响应快照。

后续相同请求如果指纹一致，则直接返回第一次响应；如果同一个幂等键对应不同请求体，则返回冲突，避免客户端误用同一幂等键创建不同业务数据。

Q: 请求指纹应该包含哪些内容？
A: 至少应包含会影响业务结果的规范化请求体字段，例如供应商名称和后续申请参数；不应把随机 trace ID 或无业务意义的字段纳入指纹。指纹计算前要固定 JSON 字段和编码规则，避免同一业务请求仅因序列化顺序不同而被误判为冲突。

Q: 两个相同幂等请求同时到达时，如何处理？
A: 不能只依赖 JVM 锁，因为服务可能有多个实例。两个请求会同时尝试写入幂等记录，数据库唯一约束只允许一个成功。另一个请求捕获唯一约束异常后，在新事务中重新读取已经提交的幂等记录，并根据请求指纹返回原始响应。

这里使用新事务很重要，因为原事务发生约束异常后通常已经被标记为回滚，不能继续在同一个事务中可靠查询和提交。

Q: 数据库唯一约束异常为什么不能直接在当前事务里查询记录？
A: 在 PostgreSQL 事务中，唯一约束异常通常会使当前事务进入回滚状态。即使后续查询语句看似执行，也不能保证继续提交；因此应退出失败事务，在 `REQUIRES_NEW` 或新的事务中读取已经提交的幂等记录，再执行回放或冲突判断。MyBatis 只负责执行 SQL，不会改变 PostgreSQL 的事务语义。

Q: 为什么不能只用 Redis 做接口幂等？
A: Redis 可以做高性能短期去重，但单独使用时需要处理过期、持久化、主从切换、网络分区和业务数据库提交顺序等问题。对于创建申请这种必须保留业务结果的操作，最终仲裁应放在具有唯一约束的持久化数据库中。

当前项目没有把 Redis 作为运行依赖，而是使用 PostgreSQL 持久化幂等记录，优先保证重启、多实例和故障恢复后的正确性。

Q: 审批状态为什么使用乐观锁？
A: 审批完成是并发更新场景，多个消费者或请求可能同时读取同一个旧状态。如果没有乐观锁，后提交的事务可能覆盖先提交的状态，导致审批链路倒退或状态丢失。

项目使用 MyBatis 显式条件更新管理申请和流程实例的版本号：`UPDATE ... SET state_version = state_version + 1 WHERE id = ? AND state_version = ?`。更新受影响行数为 0 时说明版本冲突，应用层转换为乐观锁异常并返回明确的冲突响应，要求调用方重新读取最新状态。

Q: 乐观锁冲突时，为什么返回 409，而不是简单重试？
A: 冲突说明客户端提交的操作基于过期状态，服务端无法替客户端决定是否覆盖最新审批结果。返回 409 能让调用方重新查询当前状态并根据业务决定是否再次操作；服务端自动重试可能把用户已经撤销或其他角色完成的状态误推进。

Q: 数据库唯一约束和 MyBatis 条件更新分别解决什么问题？
A: 唯一约束解决“同一业务唯一性不能被并发请求突破”，例如同一幂等作用域只能有一条记录；MyBatis 条件更新通过旧版本条件解决“同一条已存在记录不能被并发旧状态覆盖”。前者是插入竞争，后者是更新竞争，两者不能相互替代。

Q: 为什么项目从 Spring Data JPA 替换为 MyBatis？替换后承担哪些代价？
A: 项目最终选择 MyBatis，是因为当前服务的 SQL 边界比较明确，且需要直接表达 PostgreSQL 的 RLS 上下文、`FOR UPDATE SKIP LOCKED`、Outbox 认领和带版本条件的原子更新。MyBatis 让这些 SQL、返回行数和事务边界更直观，也减少了 ORM 状态管理对可靠消息和并发控制的隐式影响。

代价是需要自行维护 XML、结果映射、插入字段和版本更新逻辑；实体不会再由 ORM 自动生成 ID、时间或版本，也不会自动触发脏检查。因此当前代码在创建对象时显式初始化字段，在更新时检查受影响行数，并用集成测试验证 SQL 与 Flyway Schema 的一致性。

Q: MyBatis 能不能替代事务管理？
A: 不能。MyBatis 负责 SQL 映射和执行，事务仍由 Spring `@Transactional` 与数据库连接管理。申请和 Outbox 是否同事务、RLS 的 `SET LOCAL` 是否绑定当前事务、消息发送是否在事务外，仍然由应用服务和事务边界决定。

Q: MyBatis 条件更新如何判断乐观锁冲突？
A: `UPDATE` 的 `WHERE` 同时匹配主键和旧版本号；返回 1 表示更新成功，返回 0 表示记录不存在、租户不可见或版本已被其他请求推进。应用服务将 0 转成 `OptimisticLockingFailureException`，HTTP 层返回 409，消息消费场景则交给重试或幂等策略处理。

Q: PostgreSQL RLS 如何实现租户隔离？
A: 请求先通过 JWT 认证，服务从已验证的 JWT 中获取 `tenantId`，不信任客户端自行声明的有效租户身份。业务事务开始时通过 `SET LOCAL` 设置事务级 `app.tenant_id`，RLS policy 使用该值限制当前事务能读取和写入的数据。

业务连接使用非超级用户，并对关键业务表启用 `FORCE ROW LEVEL SECURITY`，防止普通业务查询绕过策略。应用层仍会保留租户条件和上下文校验，但 RLS 是数据库层的最终防线。

Q: 为什么使用 `SET LOCAL`，而不是普通 `SET`？
A: `SET LOCAL` 只在当前数据库事务内生效，事务结束后自动恢复，适合连接池环境。普通 `SET` 可能把上一个请求的租户上下文留在复用连接上，造成严重的跨租户数据泄露风险。

Q: 如果忘记初始化 `app.tenant_id`，会发生什么？
A: RLS policy 应在租户上下文缺失时拒绝访问或返回空结果，而不是默认放开查询。应用层需要在事务入口初始化上下文，并使用集成测试验证租户 A 无法读取租户 B 的数据；数据库角色也必须是不能绕过 RLS 的业务账号。

Q: 为什么 IAM 的 RLS 处理和业务服务不同？
A: 登录发生在用户尚未认证之前，服务必须先根据登录请求中的租户和用户名查找用户，因此 IAM 登录查询无法完全依赖已建立的 JWT 租户上下文。当前实现将 IAM Schema 作为认证前置场景的特殊处理，并通过独立账号、登录参数校验、JWT 签名租户声明和安全审计进行补偿。

Supplier 和 Workflow 的业务数据则在 JWT 已认证后访问，使用非超级用户和强制 RLS 做租户隔离。未来如果增加 IAM 管理接口，需要重新评估 IAM Schema 的管理边界。

Q: IAM 登录依赖请求中的 tenantId，会不会造成租户伪造？
A: 登录前的 tenantId 只能作为查找范围，不能被直接当成已认证身份。系统仍需验证用户名、密码、用户状态和租户状态，成功后由服务端把租户写入签名 JWT；后续业务服务只信任经过签名校验的 JWT 租户声明，不信任客户端自带的租户 Header。

Q: JWT 和 Refresh Token 如何配合？
A: 登录成功后 IAM 签发短生命周期 Access Token 和持久化 Refresh Token。Access Token 用于跨服务认证，包含用户、租户和角色等声明；Refresh Token 用于换取新的令牌对。

刷新时执行 Refresh Token 轮换，旧令牌被标记为已使用或撤销，避免同一个刷新令牌被无限复用。登出会撤销当前 Refresh Token。IAM 多副本会按保留窗口和批量上限清理过期或长期撤销的令牌，并用 `FOR UPDATE SKIP LOCKED` 避免清理任务互相争抢。签名密钥要求使用足够长度的随机 Base64 值，生产环境通过外部 Secret 注入。

Q: Refresh Token 轮换如何防止令牌重放？
A: 每次刷新都使旧 Refresh Token 失效并签发新的令牌对。攻击者重放已经使用过的旧令牌时，服务端应拒绝请求；在更高安全等级下还可以检测令牌族重放并撤销同一会话的全部令牌。令牌值不能写入日志或审计表。

Q: Access Token 被盗后，当前设计能立即撤销吗？
A: 短生命周期 Access Token 通常不能在每次请求都查数据库撤销，当前设计主要依赖较短过期时间和 Refresh Token 撤销/轮换。若业务需要立即撤销，可增加 Token 黑名单、会话版本或集中式授权检查，但会引入 Redis/数据库查询和可用性成本。

Q: 安全审计记录哪些内容？哪些内容不能记录？
A: 当前 IAM 对登录成功、登录失败和登出进行审计，记录租户、用户、事件类型、结果、时间、IP/请求上下文和 trace ID 等可用于排查和追责的信息。

不能记录明文密码、Access Token、Refresh Token 或完整敏感请求体。审计数据本身也要避免成为新的敏感信息泄露源。

Q: 为什么使用 Testcontainers，而不是 H2？
A: 项目使用 PostgreSQL RLS、Flyway、schema、非超级用户和 PostgreSQL 特有 SQL，H2 无法真实还原这些行为。Testcontainers 可以在测试中启动真实 PostgreSQL，验证迁移、权限和 RLS 策略。

五个使用 PostgreSQL 的服务测试模块统一使用 `@Testcontainers` 管理容器，并用 `@DirtiesContext(AFTER_CLASS)` 防止 Spring 测试上下文复用已关闭容器连接池。

Q: 为什么 Testcontainers 的生命周期会和 Spring Context 缓存冲突？
A: JUnit 扩展可能在测试类结束后停止静态容器，而 Spring TestContext 仍可能缓存同一应用上下文和连接池。后续测试复用这个上下文时，连接池指向已关闭的容器，就会出现连接校验失败或进程长时间等待。`@DirtiesContext(AFTER_CLASS)` 让上下文在容器生命周期结束前后不再被错误复用。

Q: 完整 Maven 测试为什么可能卡在 Testcontainers？如何排查？
A: 先区分测试断言失败、Spring Context 初始化失败和 Docker daemon 不可用。可以检查 surefire XML 的 `failures`/`errors`、查看 Testcontainers 初始化日志、执行 `docker ps` 或访问 Docker socket，并确认 Maven 进程和 surefire 子进程状态。

本项目曾出现 Docker socket 无响应导致 Testcontainers 初始化长时间等待。代码侧已统一容器生命周期，但如果 Docker Desktop 本身无响应，仍然需要先恢复 Docker daemon，不能把“surefire 报告为 0 failures”当作 Maven 进程完整成功退出。

Q: 如何判断是测试失败，还是 Docker 环境导致卡住？
A: 先查看 surefire XML 是否存在 `failures` 或 `errors`，再看 Maven 和 surefire 子进程最后停在哪一步。若日志停在 Docker client 初始化，且 `docker ps`、Docker socket `_ping` 也无响应，应判定为环境问题；修复 Docker 后必须重新运行 Maven，并以进程正常退出和完整 Reactor 汇总为准。

Q: Helm Chart 如何防止部署默认密码？
A: Chart 对 JWT 签名密钥、五个业务数据库密码和对象存储密钥使用 Helm `required` 校验，并拒绝已知占位值。也支持通过 `global.existingSecret` 引用预先创建的 Kubernetes Secret，避免 Chart 生成生产凭据。

CI 中使用仅用于校验的临时值执行 `helm lint` 和 `helm template`，同时验证缺少凭据时渲染必须失败。真实密钥不会提交到仓库。

Q: 生产镜像如何保证来源可追溯且没有明显漏洞？
A: 主分支 CI 为六个应用服务和一个备份镜像发布完整 Git 提交 SHA 标签，先用 Trivy 扫描不可变标签，再使用 GitHub OIDC 生成 Cosign keyless 签名。Helm 发布前通过 `verify-flowmesh-images.sh` 校验七个镜像的提交标签和签名，Kyverno 策略还会在集群准入阶段拒绝未签名镜像；目标集群仍需配置持续漏洞扫描。

Q: 配置 `global.existingSecret` 后，Chart 会自动创建这个 Secret 吗？
A: 不会。设置 `existingSecret` 表示 Secret 由集群管理员或其他部署流程预先创建，Chart 只引用它。这样可以避免 Helm release manifest 包含生产凭据；部署前必须验证 Secret 存在且包含 `JWT_SIGNING_KEY`、五个业务数据库密码和对象存储密钥等必需键。

Q: 为什么使用 Docker Compose 和 Helm 两套部署方式？
A: Docker Compose 面向本地开发和演示，负责启动 PostgreSQL、RocketMQ 和应用服务，降低本地运行门槛。Helm 面向 Kubernetes 部署，提供 Deployment、Service、Secret 引用、健康探针、资源配置和副本数配置。

两套配置的目标不同：Compose 优先本地可用性，Helm 优先集群部署规范和 Secret 管理，不能把 Compose 的单 Broker 演示拓扑直接当成生产高可用方案。

Q: Gateway 和业务服务扩容后，如何保证消息和任务不会重复处理？
A: Outbox 发布使用数据库认领和条件更新，消费者使用事件 ID、Inbox 或业务唯一约束幂等。扩容只能提高处理能力，不能替代幂等设计；还需要补充双副本并发、Broker ACK 后宕机和重复投递的集成测试，才能证明扩容后的行为。

Q: 项目当前有哪些明显的技术债或风险？
A:
- 完整监控平台、生产级 Broker/数据库高可用和目标集群 Chaos 故障演练仍需补充；当前已提供 Prometheus 抓取与告警样例、恢复演练脚本，核心 RocketMQ E2E 和多实例 Outbox 竞争测试已完成。
- 当前 workflow 是内部流程状态实现，尚未接入 Camunda 8；这属于明确的编排替换路线，不影响当前事件契约。
- Redis 缓存和外部邮件/短信通道仍未接入；Gateway/IAM Redis 限流、MinIO、独立风险/通知服务、DLQ 查询/重放/审计和对账入口已接入。
- Compose 仍是单机演示拓扑；Helm 已提供 Gateway、双副本、HPA、PDB、Ingress 和业务入口 NetworkPolicy，但外部依赖 HA 仍由目标平台负责。
- 当前已具备基础业务/消息指标、Gateway 限流结果指标、HTTP Trace ID、按消费者区分的消息处理耗时指标和可选 OTLP Trace 出口；生产 Collector、告警通知路由和大规模并发压测仍需在目标环境完成。

Q: 当前实现扩容时最可能的瓶颈是什么？
A: 主要瓶颈包括 Outbox 扫描和认领 SQL、RocketMQ 发布吞吐、消费者数据库事务、PostgreSQL 连接池以及消息堆积。当前已经有消息处理耗时直方图和 P95 告警，但扩容前仍应通过指标和压测确认瓶颈，再调整批大小、索引、连接池和消费者并发，不能只增加 Pod 副本。

主动说明边界比把设计蓝图中的规划内容包装成已完成能力更可信。

Q: 如果让你继续迭代，下一步会做什么？
A: 下一步优先完成真实集群的 Ingress/TLS、NetworkPolicy、HPA/PDB 和数据库/RocketMQ/Redis HA 演练，再做大规模并发压测和告警通知值班演练；当前应用正确性链路已经通过真实 RocketMQ E2E、多实例竞争、DLQ 运维和对账验证。

在此基础上再评估 Camunda 8 和 Redis 缓存，并补齐外部通知通道；MinIO、风险和通知审计已经是当前运行链路的一部分，不需要重复建设。

Q: 为什么下一步优先补监控告警和压测，而不是先接入更多中间件？
A: 核心消息链路已经通过 ACK、重试、幂等、多实例竞争和真实 Broker E2E 验证。下一步补监控告警和压测，可以量化堆积、失败率、处理耗时与扩容边界，再决定是否引入 Redis 缓存或 Camunda。

Q: 这个项目最能体现你的能力是什么？
A: 最能体现的是对分布式系统一致性边界的理解：不把消息队列、数据库或事务包装成“天然恰好一次”，而是从业务数据归属、本地事务、Outbox、幂等、乐观锁、RLS 和失败恢复几个层面组合设计。

同时项目保留了清晰的能力边界和可验证的测试、部署流程，能够说明不仅完成了功能，也考虑了多实例、故障和安全场景。

Q: 如果只有 3 分钟，你会选择哪个技术点展开？
A: 优先展开“Supplier 创建申请 + Outbox + Workflow 消费”的链路：先讲本地事务为什么同时写业务表和 Outbox，再讲 `FOR UPDATE SKIP LOCKED` 如何认领、发送成功后的状态确认、宕机后的重复窗口，以及消费者如何用幂等吸收重复消息。最后主动说明这是至少一次投递和最终一致性，而不是恰好一次。
